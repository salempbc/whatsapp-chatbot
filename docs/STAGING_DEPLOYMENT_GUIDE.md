# SPBC Church CMS 2.1 — Staging Deployment Guide

**Target Application:** Salem Primitive Baptist Church (SPBC) Church CMS 2.1  
**Target Environment:** Isolated Cloud Staging (Render Web Service)  
**Database Target:** `spbc_staging` (MongoDB Atlas Dedicated Database)  
**Last Updated:** October 5, 2026  

---

## 1. Prerequisites

Before initiating the staging deployment, ensure you have the following access rights and accounts prepared:

1. **Render Account:** Access to [Render Dashboard](https://dashboard.render.com/) with permission to provision Web Services.
2. **MongoDB Atlas Account:** Access to MongoDB Atlas cluster with administrative credentials to connect to database `spbc_staging`.
3. **Telegram Account & [@BotFather](https://t.me/BotFather) Access:** Ability to create and configure a dedicated staging bot.
4. **Staging Administrator Telegram ID:** Numeric Telegram user ID of the authorized staging tester (obtainable via [@userinfobot](https://t.me/userinfobot)).

---

## 2. Environment Variables Specification

The staging service must be configured with dedicated staging credentials. **Never reuse production credentials in staging.**

```ini
# --- STAGING ENVIRONMENT CONFIGURATION ---
NODE_ENV=staging
PORT=3000

# Isolated Staging Database (DO NOT use production cluster URI)
MONGO_URI=<STAGING_MONGO_URI>
MONGO_DB_NAME=spbc_staging

# Staging Telegram Bot Token (Dedicated bot from @BotFather)
BOT_TOKEN=<STAGING_BOT_TOKEN>

# Staging Administrator Telegram User ID (Numeric ID of tester)
ADMIN_ID=<STAGING_ADMIN_ID>

# WebApp Standalone Access Secret (Minimum 32 random hex characters)
ADMIN_SECRET=<STAGING_ADMIN_SECRET>

# Public WebApp HTTPS URL (Generated by Render, e.g. https://spbc-staging.onrender.com)
WEBAPP_URL=<STAGING_WEBAPP_URL>

# Optional: Google Gemini AI Configuration for pastoral wishes
GEMINI_API_KEY=<STAGING_GEMINI_API_KEY>
GEMINI_MODEL=gemini-1.5-flash

# Optional: Shared secret for Telegram webhook security
WEBHOOK_SECRET=<STAGING_WEBHOOK_SECRET>
```

> [!WARNING]
> Never commit real credentials to Git, documentation, pull requests, or issue tickets.

## 3. MongoDB Staging Isolation & Index Verification

### 3.1 Database Isolation Invariant
The staging application automatically targets `spbc_staging` when `MONGO_DB_NAME=spbc_staging` is provided, completely isolating staging records from production.

### 3.2 Index Verification Command
Connect to your staging cluster via `mongosh` and verify that required compound indexes exist:

```javascript
// Connect to staging database
use spbc_staging;

// 1. Members Collection Indexes
db.members.createIndex({ isDeleted: 1, isActive: 1, birthday: 1 }, { background: true });
db.members.createIndex({ isDeleted: 1, isActive: 1, wedding: 1 }, { background: true });
db.members.createIndex({ familyName: 1, name: 1 }, { background: true });
db.members.createIndex({ status: 1, isDeleted: 1 }, { background: true });
db.members.createIndex({ name: 1 }, { unique: true });

// 2. ChurchEvents Collection Indexes
db.churchevents.createIndex({ startDate: 1, status: 1 }, { background: true });
db.churchevents.createIndex({ category: 1, startDate: 1 }, { background: true });

// 3. Tasks Collection Indexes
db.tasks.createIndex({ status: 1, dueDate: 1 }, { background: true });
db.tasks.createIndex({ category: 1, priority: 1 }, { background: true });

// 4. AuditLogs Collection Indexes
db.auditlogs.createIndex({ createdAt: -1 }, { background: true });
db.auditlogs.createIndex({ entity: 1, entityId: 1 }, { background: true });

// 5. GreetingLogs Collection Indexes
db.greetinglogs.createIndex({ dateKey: 1, year: 1, memberId: 1, type: 1 }, { unique: true });
db.greetinglogs.createIndex({ status: 1 }, { background: true });
```

## 4. Telegram Staging Bot Preparation

A dedicated staging bot ensures that test interactions and morning review cards never collide with production church operations.

### Step-by-Step BotFather Configuration:
1. Open Telegram and message [@BotFather](https://t.me/BotFather).
2. Send `/newbot`.
3. Set Bot Name: `SPBC Church CMS (Staging)`.
4. Set Username: `spbc_staging_bot` (or similar available username ending in `bot`).
5. Copy the HTTP API token: This is your `<STAGING_BOT_TOKEN>`.
6. Configure Menu Button:
   - Send `/setmenubutton`.
   - Select your staging bot.
   - Set button text: `🌐 Open CMS`.
   - Set URL: `https://<STAGING_WEBAPP_URL>`.
7. Configure Default Commands:
   - Send `/setcommands`.
   - Select your staging bot.
   - Paste:
     ```text
     start - Open CMS dashboard
     review - Today's celebration greeting deck
     events - Church calendar and scheduled services
     tasks - Administrative tasks & follow-up queue
     stats - Congregational demographics & health audit
     ping - Liveness check
     help - Administrative user guide
     ```

## 5. Render Staging Web Service Setup

Render hosts the Express API, Telegram bot engine, background scheduler, and Vue 3 Mini App.

### Option A: Using the Blueprint (`render.yaml`)
1. In the Render Dashboard, navigate to **Blueprints**.
2. Click **New Blueprint Instance**.
3. Connect repository `salempbc/whatsapp-chatbot`.
4. Select the branch containing the 2.1 release.
5. Render detects [`render.yaml`](../render.yaml) automatically.
6. In the environment variable prompts, provide the sensitive staging values for:
   - `MONGO_URI`
   - `BOT_TOKEN`
   - `ADMIN_ID`
   - `ADMIN_SECRET`
   - `WEBAPP_URL`
   - `GEMINI_API_KEY` (optional)
7. Click **Apply**.

### Option B: Manual Web Service Creation
1. In Render Dashboard, click **New +** -> **Web Service**.
2. Connect repository `salempbc/whatsapp-chatbot`.
3. Configure Service Settings:
   - **Name:** `spbc-church-cms-staging`
   - **Region:** Oregon (or closest to administrator)
   - **Branch:** `main`
   - **Runtime:** `Node`
   - **Build Command:** `npm install`
   - **Start Command:** `npm start`
   - **Instance Type:** `Starter` (or `Free`)
4. Configure Health Check:
   - **Health Check Path:** `/ping`
5. Configure Environment Variables (under **Environment** tab):
   - Add all variables listed in Section 2.
6. Click **Create Web Service**.

## 6. Post-Deployment Verification Protocol

Once the Render build completes and transitions to "Live":

### 6.1 Liveness & Health Verification
Execute against the deployed URL:

```bash
# 1. Root Ping Check
curl -i https://<STAGING_WEBAPP_URL>/ping
# Expected: HTTP/1.1 200 OK, Body: pong

# 2. API Ping Check
curl -i https://<STAGING_WEBAPP_URL>/api/ping
# Expected: HTTP/1.1 200 OK, Body: pong

# 3. Telemetry & Diagnostics Check
curl -s https://<STAGING_WEBAPP_URL>/api/diagnostics | jq .
# Expected: { "status": "healthy", "database": { "status": "connected" }, ... }
```

### 6.2 Staging Smoke Test Sequence
1. **Admin Authorization Check:** Send `/start` from `<STAGING_ADMIN_ID>` in Telegram -> Verify dashboard appears with "Open Web Admin Dashboard" button.
2. **Fail-Closed Security Check:** Send `/start` and `/ping` from a non-admin account -> Confirm bot does not respond.
3. **WebApp Verification:** Open the Mini App inside Telegram -> Verify tabs `Members`, `Events`, `Tasks`, `Reports`, `Wishes`, `Settings`.
4. **Member Lifecycle Test:** Create a disposable member record, verify duplicate detection alert triggers when entering duplicate names/phones.
5. **Event & Calendar Test:** Create an event, download `.ics` file.
6. **Task Management Test:** Create a task, mark as completed.
7. **Wishes Test:** Trigger `/review`, test "Copy Message for WhatsApp".

## 8. Rollback Procedure

If a critical runtime issue occurs during staging validation:
1. In the Render Dashboard for `spbc-church-cms-staging`, navigate to **Deploys**.
2. Identify the previous stable commit.
3. Click **Rollback** to immediately restore the prior release.
4. Database records in `spbc_staging` remain non-destructive and backward-compatible.
